# Phase 7 Website Memory Update Decision Policy

## 1. Why Website Maintenance Needs a Memory Update Decision Rule

### Why We Should Not Update Memory Every Time
- Not every Website maintenance task changes the project’s long-term meaning.
- Some changes are local, low-risk, and already covered by the existing phase docs.
- If we update memory too often, it becomes noisy and less useful.

### Why We Also Cannot Skip Memory Updates Completely
- Some maintenance changes alter the project status, risk posture, or boundary language.
- If memory is not updated after those changes, future chats may inherit the wrong conclusion.
- The memory files are the operational recall layer; they must stay aligned with the real state.

### Why Memory / Handoff Must Match Real Contract Changes
- If a maintenance task changes what the project means, what it protects, or what comes next, future chats need that reflected immediately.
- Handoff is especially important when the next person must know the boundary without reading the entire doc chain.
- Memory exists to preserve the current truth, not just the history of edits.

---

## 2. When Memory Does Not Need to Be Updated

### No-Update Situations
- the maintenance is low-risk and local
- the change does not alter project status, boundary, risk, or next-step language
- the change is limited to wording, clarity, or a small verified-safe fix
- the change is fully covered by the existing docs and does not change what future chats must know

### Why These Can Skip Memory
- they do not change the meaning of the project state
- they do not change the Telegram hold position
- they do not change the Website-first protection posture
- they do not affect handoff decisions

### Typical Examples
- doc wording correction
- small checklist clarification
- narrow, behavior-preserving maintenance that stays inside the sample boundary

### Rule of Thumb
- If the change would not alter the answer to “What is the current boundary?” or “What is the next unique priority action?”, memory probably does not need an update.

---

## 3. When Memory Must Be Updated

### Mandatory-Update Situations
- the maintenance changes the project state description
- the maintenance changes the risk posture
- the maintenance changes the boundary language for Website or Telegram
- the maintenance changes the next-step action or hold position
- the maintenance changes what future chats must read first
- the maintenance changes the operational conclusion even if the version stays the same

### Why These Must Be Written Back
- future chats depend on memory to restate the current truth quickly.
- if the long-term memory is stale, the same mistake will recur.
- handoff must reflect the actual boundary, not an older version of it.

### Key Triggers for Mandatory Update
- a change alters the project phase wording
- a change updates the priority object description
- a change changes whether Telegram is on hold or allowed
- a change affects the planned next action
- a change would cause a new chat to answer differently than the current truth

---

## 4. When Handoff or Memory Should Be Updated Even If Version Does Not Change

### Update Memory / Handoff Without Version Bump When
- the project position changes but the product version does not
- the boundary wording changes and future chats must know it
- the hold position is reaffirmed in a stronger or clearer way
- the next unique priority action becomes more explicit
- the new documents add a decision rule that future chats must follow

### Which Memory Files Are Most Likely to Need Sync
- `01_project_status.md` when the phase, current position, or priority action changes
- `02_completed_work.md` when a new document chain or milestone is finished
- `03_next_phase_plan.md` when the next action or future condition changes
- `04_risks_issues.md` when risk interpretation changes or a new misread risk needs to be remembered
- `05_handoff_for_new_chat.md` when the boundary instructions for future chats change

### When Only Partial Memory Needs Updating
- if the change only affects a single area, update only the memory files that carry that meaning
- example: a pure boundary clarification may only need `01`, `03`, and `05`
- example: a risk interpretation change may only need `01`, `03`, and `04`

### When All 5 Memory Files Should Be Synced
- when the project conclusion changes
- when the hold position is reaffirmed with new operational rules
- when the new document chain changes what future chats must do first
- when the safe continuation model needs a full refresh across status, completed work, next phase, risks, and handoff

### When `05_handoff_for_new_chat.md` Must Be Updated
- when the new-chat reading order changes
- when the boundary language for new chats changes
- when a new document becomes mandatory reading before action
- when future chats must be told a stronger “do not start real Telegram development” rule

---

## 5. How to Decide Whether to Sync Completed / Risks / Next Phase

### Update `02_completed_work.md` When
- a new document is completed that materially adds to the Phase 7 control system
- the project has a new documented milestone or closure point
- the completion changes what Phase 7 is now considered to have finished

### Update `04_risks_issues.md` When
- a maintenance task reveals a new recurring misread risk
- the boundary risk language becomes sharper or broader
- the project needs a fresh reminder about what can still go wrong

### Update `03_next_phase_plan.md` When
- the default next action changes
- the conditions for future Telegram work become clearer
- the current hold position needs to be reflected as the next planned posture

### Update `01_project_status.md` When
- the phase label changes in a way future chats must know immediately
- the current completion point changes
- the current boundary wording changes
- the next unique priority action changes
