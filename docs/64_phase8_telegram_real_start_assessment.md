# Phase 8.0 Telegram Real Start Assessment

## 1. 当前真实路线切换说明

ChatFlow Pro 现在进入的不是继续追加 Telegram hold 文档的阶段，而是**Telegram 最小真实开发启动评估**阶段。

这里的路线切换很明确：
- Website 仍是第一真实稳定样板
- Telegram 不再继续无限期 hold
- 当前不是直接实装，而是先做最小真实开发启动评估

这一步的意义是把“长期防守”切换成“是否可启动、从哪里启动、怎么控制风险”的判断层，而不是立刻把 Telegram 全功能铺开。

## 2. 为什么现在进入 Phase 8.0

### 为什么不能继续无上限追加 hold 文档

Phase 7 的治理链已经把 Telegram 的 planning、readiness、gate、protection、blocker、minimal-change、isolation、regression 和 change-gate 讲清楚了。继续追加 hold 文档不会增加新的可执行信息，只会延后真正需要回答的问题：**现在到底能不能启动最小真实开发**。

### 为什么现在要从治理完成转向启动评估

治理文档的作用是定义边界和约束，不是永久替代决策。现在已经有足够的控制面材料来判断下一步，因此下一阶段应该转向评估：
- 是否具备最低启动条件
- 从哪个入口开始最安全
- 如何避免破坏 Website 基线

### 这一步与直接开发的边界差异

启动评估不是开发实施。它只回答“能不能、从哪儿、怎么控风险”，不做 Telegram 的完整功能扩展。真正进入开发时，才会写代码；而且只能先做最小闭环，不得一上来扩成完整 Telegram 功能面。

## 3. Telegram 最小真实开发的候选入口

### 唯一建议入口

Telegram 最小真实开发的第一入口，建议是：**最小 inbound 接入 + 最小 response 回传闭环**。

换句话说，先把 Telegram 的消息进来、经过现有统一链路、再把最小回复发回去，做成一个可验证的最小闭环，而不是先做完整 bot 功能、菜单、状态机或复杂交互。

### 为什么选这个入口

因为它最能验证 Telegram 是否真的能接入现有结构，同时对共享面改动最小。这个入口可以最快暴露真正风险：
- webhook / auth 是否可用
- session / context 是否能顺利传递
- outbound sender 是否能按统一形状返回结果
- Website 是否会被共享 contract 变更影响

### 对现有 Website 稳定样板的影响范围

影响范围应严格限制在共享 contract 和最小 channel adapter 边界内，不应扩散到 Website 现有闭环的业务逻辑、样板行为或回归路径。只要是会改变 Website 稳定行为的扩展，都不应在第一轮启动里顺手做。

### 是否满足最小变更原则

是，前提是只做最小 inbound / outbound 闭环，不扩功能、不加旁路能力、不顺带重构 shared pipeline。若超过这个范围，就不再算最小变更。

## 4. 启动前置条件检查

### 当前已具备什么

- Website 已是稳定样板，并且是可回归参考点
- Phase 7 的 Telegram 控制文档已经形成完整边界
- 统一 inbound / outbound 的结构基础已经存在
- 项目已经明确知道 Telegram 不能用“文档写完”来冒充“可以开发”

### 当前还缺什么

- Telegram 最小真实接入的工程拆分还未正式落地
- Telegram 真实 webhook / auth / transport / sender 的实施细节仍未完成
- 还没有形成一轮可直接执行的最小开发工作包
- 还没有明确确认哪些契约可以动、哪些必须保持不动

### 哪些是必须先补齐的硬前置

- 最小启动入口必须明确
- Shared contract 变更边界必须明确
- Website 回归验证点必须明确
- 不能把“评估通过”误当成“全面开发批准”

### 哪些可以进入开发时再补

- Telegram 更完整的功能面
- 更细的交互状态扩展
- 后续的可观测性增强
- 更丰富的 bot 行为与辅助流程

## 5. 风险评估

### Website 回归风险

这是最高优先级风险。只要 Telegram 的接入会改变 Website 的稳定闭环，就必须先停下来重新判断。

### 共用 contract / pipeline 变更风险

Telegram 最容易带来的风险不是 Telegram 本身，而是 shared contract、pipeline、mapping、sender 结构被顺手改大。一旦 shared 面被扩大，Website 回归成本会迅速上升。

### 误把评估当成批准开发的风险

这一步只是评估，不是放行。最大的风险是把“开始评估”误读成“已经批准全面开发”，然后不自觉扩大实现范围。

### 过早扩大 Telegram 范围的风险

如果一开始就想同时做 webhook、状态机、菜单、用户配置、管理员功能，那就会直接偏离最小真实开发原则，增加回归和重构风险。

## 6. 启动建议结论

### 结论：有条件启动

当前结论不是直接建议全面开发，也不是继续无限期暂缓，而是：**有条件启动**。

### 如果进入最小真实开发，第一步只允许做什么

只允许做**Telegram 最小 inbound 接入 + 最小 response 回传闭环**，并在同一轮里加入 Website 回归验证。除此之外，不得顺手扩成完整 Telegram 功能面。

### 如果不建议立即进入，还需要先补什么

如果评估结果认为仍不宜启动，则应先补齐：
- 最小入口定义
- Shared contract 变更边界
- Website 回归检查清单
- 最小开发工作包拆分

### 必须给出的明确判断

当前并不是“继续 hold 到无限期”，也不是“全面实装已经就绪”，而是：**条件够进入最小真实开发评估，并在满足最小闭环前提时有条件启动**。

## 7. 后续执行守则

- 最小变更
- 先隔离后接入
- Website 回归保护优先
- 不得一开始扩成完整 Telegram 功能面
- 不得把评估结果自动升级成全面开发许可

## 8. 本轮结论

Phase 8.0 的本轮结论是：**Telegram 可以进入有条件启动的最小真实开发评估路径**。

下一轮如果正式进入开发，只能从最小 inbound / outbound 闭环开始，并且必须把 Website 稳定样板的回归保护放在第一位。
