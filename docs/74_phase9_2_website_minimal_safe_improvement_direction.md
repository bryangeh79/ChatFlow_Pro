# Phase 9.2 Website Minimal Safe Improvement Direction

## 1. 当前 Website baseline 内可考虑的补强候选方向

在不破坏 Website baseline 的前提下，下一轮可考虑的最小补强方向主要有以下几类：

### A. 更细的可观测性补强

目标是让现有 Website 真实闭环更容易被确认，而不是改变其行为。

### B. 更轻的维护性修补

目标是做一些不改变语义的小修正，让当前闭环更容易维护。

### C. 更清晰的边界 / 验证补充

目标是让 Website 的可维护边界更明确，更容易判断下一步是否安全。

### D. 极小的稳定性增强

目标是补一点安全性或可读性，但不触碰 Website 真实闭环语义。

### E. 其他不破坏 baseline 的微小改进方向

比如最小的文档对齐、最小的验证说明增强、最小的回归提示补足。

## 2. 每个候选方向的评估

### A. 更细的可观测性补强

**价值：**
- 最有助于快速确认 Website 是否仍然稳定
- 对回归判断非常直接

**风险：**
- 低到中低，但如果把“可观测性”做成“新行为”，就会越界

**是否会碰到受保护边界：**
- 可能会碰到，但只要不改语义，一般可控

**是否容易引发语义变化：**
- 低，前提是只补可见性，不改结果形状或结果含义

**是否适合作为下一轮唯一动作：**
- 适合，且是当前最稳妥的选择

### B. 更轻的维护性修补

**价值：**
- 对后续维护有帮助
- 适合处理明显的小瑕疵

**风险：**
- 低到中等，容易在“顺手修一下”时改过头

**是否会碰到受保护边界：**
- 有可能，尤其是动到 Website 入口或结果语义时

**是否容易引发语义变化：**
- 中等

**是否适合作为下一轮唯一动作：**
- 不如可观测性补强稳妥

### C. 更清晰的边界 / 验证补充

**价值：**
- 很适合当前阶段
- 能让 baseline 更容易判断是否安全

**风险：**
- 低，但容易沦为纯文档化，没有实质帮助

**是否会碰到受保护边界：**
- 通常不会直接碰核心边界

**是否容易引发语义变化：**
- 很低

**是否适合作为下一轮唯一动作：**
- 适合，但如果只是文档补充，收益可能不如可观测性补强直接

### D. 极小的稳定性增强

**价值：**
- 可以补一点保险
- 对真实闭环有一定加固作用

**风险：**
- 中低到中等，取决于是否触碰共享层

**是否会碰到受保护边界：**
- 有可能，特别是涉及 sender / contract / fallback 时

**是否容易引发语义变化：**
- 中等

**是否适合作为下一轮唯一动作：**
- 不优先

### E. 其他不破坏 baseline 的微小改进方向

**价值：**
- 可作为兜底

**风险：**
- 取决于具体内容，常常容易被泛化成“顺手做点别的”

**是否会碰到受保护边界：**
- 不确定性较高

**是否容易引发语义变化：**
- 中等偏高，取决于执行方式

**是否适合作为下一轮唯一动作：**
- 不建议

## 3. 单一推荐方向

### 唯一推荐方向

**推荐方向：更细的可观测性补强。**

### 为什么选它

因为当前 Website baseline 的稳定性已经成立，但下一轮如果要继续推进，最重要的不是加功能，而是让“是否仍然稳定”更容易确认。可观测性补强能直接帮助判断 baseline 是否受影响，而且通常不需要改语义。

### 为什么不选其他候选方向

- **不选更轻的维护性修补**：它有用，但更容易在小修小补里碰到语义边界
- **不选更清晰的边界 / 验证补充**：它通常偏文档层，价值存在但不如可观测性直接
- **不选极小的稳定性增强**：风险更依赖具体实现，容易碰到 sender / contract / fallback
- **不选其他微小改进方向**：太泛，最容易滑成“顺手做别的”

## 4. 下一轮第一动作建议

### 如果进入下一轮执行，唯一第一动作是什么

**先为 Website 当前真实闭环补最小的可观测性输出，让基线状态更容易被确认。**

### 应控制到什么范围

只控制在：
- 不改变 Website 真实闭环语义
- 不改 inbound / outbound 行为
- 不改 sender / fallback 行为
- 不碰 Telegram
- 不扩成多路线并行

### 明确不能顺手扩到哪里

不能顺手扩到：
- Telegram 继续推进
- shared core 大改
- 数据层重构
- 后台大扩展
- Website 功能面新增

## 5. memory 判断

### 当前是否达到需要更新 5 个 memory 文件的程度

不需要。

### 原因

本轮只是定义 Website baseline 内下一步最小安全补强方向，没有改变项目主路线，也没有产生新的长期边界事实。它属于阶段性方向选择，不是需要写入长期记忆的组织级变化。

## 6. 结论

下一轮在 Website baseline 内的唯一推荐补强方向是：**更细的可观测性补强**。

它最符合当前“稳基线、少改动、先确认”的需要，也最不容易把项目带回多路线和语义风险。
